Topic 01 / 07

How to Improve
Application Performance

Why fast apps win, what slows them down, and the exact tools to fix every bottleneck — from profiling to async patterns.

Profiling Caching Async DB Optimization CDN
🍕 The Pizza Shop Analogy

Imagine a pizza shop. On a normal day, one chef can make pizzas fast enough. But on Friday night, 200 people walk in at once. The single chef gets overwhelmed, orders pile up, and everyone waits an hour for cold pizza.

The shop has a performance problem. What can they do?

  • Write orders faster (better code / algorithms)
  • Keep popular toppings pre-chopped (caching)
  • Hire more chefs (more servers)
  • Use the industrial oven instead of the small one (better hardware/tools)
  • Take phone orders ahead of time (async, queues)
  • Open a second counter for drinks so the main counter isn't blocked (separate concerns)

Application performance is exactly this — your app is the chef, users are the customers, and every fix is a way to serve more people, faster, without dropping orders.

Application performance is measured by how fast an app responds (latency), how many requests it handles per second (throughput), and how efficiently it uses resources (CPU, memory, I/O).

Performance problems have a root cause. The most common are:

  • CPU-bound — computation is too expensive (e.g. sorting a million records on every request)
  • I/O-bound — waiting on disk reads, network calls, database queries
  • Memory-bound — objects are created and garbage-collected too often
  • Concurrency-bound — requests queue up because only one thread handles them

Rule #1: Never guess. Always profile (measure) first to find the actual bottleneck. Optimising the wrong thing wastes time and sometimes makes things worse.

Scenario: User Dashboard API taking 3–5 seconds

❌ Before — Slow

Every request hits the database 4 times: once for user, once for orders, once for notifications, once for stats. All synchronous. No caching.

# BEFORE: 4 sequential DB hits, ~3000ms
def get_dashboard(user_id):
    user   = db.query("SELECT * FROM users WHERE id = ?", user_id)       # 200ms
    orders = db.query("SELECT * FROM orders WHERE user_id = ?", user_id) # 800ms (no index)
    notifs = db.query("SELECT * FROM notifications WHERE uid = ?", user_id) # 600ms
    stats  = db.query("SELECT COUNT(*), SUM(total)...", user_id)         # 1400ms (full scan)
    return build_response(user, orders, notifs, stats)
    # Total: ~3000ms 😬
✅ After — Fast

Add indexes, run queries in parallel, cache the result. Same data, 95% faster.

# AFTER: parallel queries + Redis cache + indexes, ~140ms
import asyncio, redis

cache = redis.Redis()

async def get_dashboard(user_id):
    cache_key = f"dashboard:{user_id}"
    cached = cache.get(cache_key)
    if cached:
        return json.loads(cached)  # ~2ms ⚡

    # Run all 4 queries IN PARALLEL (asyncio / thread pool)
    user, orders, notifs, stats = await asyncio.gather(
        db.async_query("SELECT * FROM users WHERE id = ?", user_id),       # 200ms (index)
        db.async_query("SELECT * FROM orders WHERE user_id = ?", user_id), # 80ms  (index)
        db.async_query("SELECT * FROM notifications WHERE uid = ?", user_id), # 60ms
        db.async_query("SELECT COUNT(*), SUM(total)...", user_id),         # 100ms (index)
    )
    # Longest query = 200ms (not 3000ms sum!)
    result = build_response(user, orders, notifs, stats)
    cache.setex(cache_key, 300, json.dumps(result))  # cache 5 mins
    return result
    # Total: ~140ms 🚀

What Changed

  • Indexes added on orders.user_id, notifications.uid → query time dropped 10×
  • Parallel execution with asyncio → total time = slowest query, not sum of all
  • Redis cache → repeat requests in 2ms instead of 140ms
🎙️ Exact Script
  1. Open with measurement: "Before touching any code, I'd profile the application to find the actual bottleneck — CPU, I/O, memory, or concurrency. Optimising without data is guessing."
  2. Layer the fixes: "I'd approach it in layers: first the quick wins — database indexes and query optimization, then caching hot data in Redis, then async patterns for slow background work, then horizontal scaling if we hit hardware limits."
  3. Mention numbers: "A missing index can turn a 2-second full-table scan into a 10ms indexed lookup. Redis can serve repeated reads in under 1ms vs 100ms+ from the DB. A CDN cuts static asset load times by 60–80% for global users."
  4. Trade-offs: "Caching introduces staleness — I'd use appropriate TTLs and cache invalidation. Async processing means the user doesn't get an immediate result; I'd pair it with websockets or polling for status updates."
  5. Close: "The goal is to measure → fix → measure again. Performance work is never 'done' — it evolves with traffic patterns."

How Databases Handle
Millions of Users

Indexing, sharding, replication, read replicas, and the CAP theorem — everything you need to scale from 1 to 1 billion records.

Indexing Sharding Replication CAP Theorem NoSQL
📚 The Library Analogy

Imagine a library with 10 books. The librarian can find any book instantly. Now imagine the library has 10 million books and 50,000 people walk in every day asking for books.

Problems appear fast:

  • Finding a book by hand takes forever → need a catalogue/index
  • One librarian can't serve everyone → need more librarians (replicas)
  • One building can't hold all books → split into multiple branches (sharding)
  • If the only library burns down, all books are lost → need backup copies (replication)

Databases solve exactly these problems. Every technique exists because one server, one disk, one copy is never enough at massive scale.

A database stores and retrieves structured data. At small scale, a single SQL database (PostgreSQL, MySQL) is fine. At large scale, you face three fundamental problems:

  • Read bottleneck — too many SELECT queries for one server
  • Write bottleneck — too many INSERTs/UPDATEs for one server
  • Storage limit — one machine can't hold petabytes of data

The CAP Theorem

A distributed system can guarantee at most 2 of 3: Consistency (every read sees the latest write), Availability (every request gets a response), Partition tolerance (system works even if nodes can't talk).

In practice, network partitions always happen, so you choose CP (consistent, may be unavailable) or AP (always available, may be stale). Most internet apps choose AP — you'd rather show slightly stale data than show an error.

What Changed & Why It Helped

  • Read replicas → reads distributed across 4 servers instead of 1
  • Sharding → writes split, each shard handles half the data
  • Indexes → lookup goes from O(n) table scan to O(log n) B-tree
  • Redis → repeated reads (e.g. user profile) served in <1ms
🎙️ Exact Script
  1. Open with the bottleneck: "At scale, databases face three bottlenecks: reads, writes, and storage. My approach is to tackle each layer separately."
  2. Read bottleneck: "For reads, I'd add indexes on queried columns, put a cache layer like Redis in front of the DB, and add read replicas to distribute read traffic."
  3. Write bottleneck: "For writes, I'd first optimize queries, then consider sharding — splitting data by a key like user_id — so writes distribute across multiple primaries."
  4. Numbers: "A read replica setup can handle 10× more reads. A cache hit from Redis is ~0.1ms vs 10ms+ from the DB. Sharding can horizontally scale writes linearly."
  5. Trade-offs: "Sharding adds query complexity — cross-shard JOINs become expensive. Replication lag means reads can be stale. The CAP theorem means we must choose between consistency and availability during a partition."
  6. Close: "The right architecture depends on the read/write ratio, data size, and consistency requirements. I'd always start with a single well-indexed DB and only add complexity when metrics demand it."

What Happens When
You Type a URL

DNS, TCP, TLS, HTTP, rendering — the complete 20-step journey from keypress to pixels on screen, explained precisely.

DNS TCP/TLS HTTP CDN Rendering
📮 The Letter Delivery Analogy

Imagine you want to send a letter to a friend but you only know their name, not their address. Here's what happens:

  1. You ask the phone book (DNS) — "What's the address for google.com?" It tells you: 142.250.80.46
  2. The post office opens a connection (TCP handshake) — both sides agree "I'm ready to receive"
  3. Because it's sensitive mail, you lock the envelope (TLS) so only the recipient can open it
  4. You write your request letter (HTTP GET) — "Please send me your homepage"
  5. Google's server reads the letter, prepares a reply (HTML, CSS, JS files)
  6. Your browser reads the reply and draws it on screen — layout, colours, fonts, images

All of this happens in under 200 milliseconds — faster than a blink. Every step is precisely engineered to be that fast.

The journey has network layers and browser rendering stages. Each is distinct and optimizable.

Network Phase

  • DNS resolution — translates domain name to IP. Checks: browser cache → OS cache → router cache → ISP recursive resolver → authoritative nameserver
  • TCP handshake — 3-way SYN / SYN-ACK / ACK establishes a reliable connection
  • TLS handshake — (for HTTPS) negotiates cipher suite, exchanges certificates, derives session keys. TLS 1.3 does this in 1 round-trip
  • HTTP request/response — browser sends GET, server responds with status + headers + body
  • CDN — a Content Delivery Network may intercept the request and serve cached responses from an edge node near the user

Browser Rendering Phase (Critical Path)

  • Parse HTML → build DOM (Document Object Model)
  • Parse CSS → build CSSOM (CSS Object Model)
  • Combine DOM + CSSOM → Render Tree
  • Layout — calculate element positions and sizes
  • Paint — draw pixels into layers
  • Composite — merge layers onto screen

🎙️ Exact Script (Classic Interview Question)
  1. Open with layers: "There are two phases: the network phase and the browser rendering phase."
  2. Network: "First, DNS resolves the domain to an IP — checking browser cache, OS cache, then the recursive resolver. Then a TCP handshake establishes the connection. For HTTPS, a TLS handshake encrypts traffic. Then the HTTP request goes out, ideally hitting a CDN edge node rather than the origin server."
  3. Rendering: "The browser parses HTML into the DOM, CSS into the CSSOM, combines them into a render tree, runs layout to compute positions, then paints and composites pixels."
  4. Mention HTTP/2: "Modern browsers use HTTP/2 which multiplexes multiple requests over one TCP connection, eliminating head-of-line blocking."
  5. Numbers: "DNS: 0–100ms. TCP+TLS: 40–100ms. CDN response: 5–50ms. Total: under 200ms for a well-optimized site."
  6. Optimization angle: "Performance can be improved at each step: DNS prefetch, TLS session resumption, HTTP/2, CDN, critical CSS inlining, lazy loading images."

How Caching Works

Cache-aside, write-through, eviction policies, Redis patterns, TTLs, and how to avoid the classic pitfalls: stampede, thundering herd, and stale data.

Redis Eviction TTL Write-Through Cache-Aside
📝 The School Desk Analogy

Imagine your school has a huge library with every book ever written. Every time you need a maths formula, you'd have to walk to the library, find the book, look it up, and walk back. That takes 10 minutes every time.

Smart students write the most-used formulas on a sticky note on their desk. Now it takes 2 seconds. That sticky note is a cache.

But the sticky note has limits:

  • It gets out of date — the formula changes but your note doesn't (stale data)
  • Your desk has limited space — you must remove old notes to add new ones (eviction)
  • The note expires after an exam — after which you write a fresh one (TTL)

Every caching system in computing works exactly like this sticky-note system — just much faster and at massive scale.

A cache is a fast, temporary store that holds copies of data that is expensive to compute or fetch. When a request arrives, you check the cache first (cache hit). If not found (cache miss), you fetch from source and optionally store in cache.

Cache Hit Rate

Hit rate = cache hits / total requests. A hit rate of 90% means 90% of reads skip the database entirely. Even 80% is transformative at scale.

Core Properties

PropertyWhat it meansExample
TTLTime-To-Live — how long before data expiresUser profile cached for 5 minutes

Classic Cache Problems

  • Cache stampede — many requests all miss the cache at once and hammer the DB simultaneously
  • Thundering herd — cache server restarts, all traffic hits origin together
  • Stale data — cache has old value that doesn't match DB
  • Cache poisoning — attacker injects bad data into cache

Product Page — 50,000 requests/minute for top 100 products

# BEFORE: Every request hits PostgreSQL
def get_product(product_id):
    return db.query(
        "SELECT * FROM products WHERE id = ?", product_id
    )  # 80ms per call, DB CPU 95%, 50K RPM = DB melts 🔥
# AFTER: Cache-Aside with Redis + TTL jitter
import redis, random

r = redis.Redis()

def get_product(product_id):
    key = f"product:{product_id}"
    cached = r.get(key)

    if cached:
        return json.loads(cached)  # ~0.3ms ⚡

    # Cache miss — fetch from DB (rare)
    product = db.query("SELECT * FROM products WHERE id = ?", product_id)

    # Store with TTL jitter to avoid stampede
    ttl = 300 + random.randint(0, 60)  # 5–6 minutes
    r.setex(key, ttl, json.dumps(product))

    return product

# Cache invalidation on product update:
def update_product(product_id, data):
    db.update("UPDATE products SET ... WHERE id = ?", data, product_id)
    r.delete(f"product:{product_id}")  # evict stale cache

Result

  • Hit rate: ~97% (top 100 products almost always cached)
  • DB queries: 50,000/min → ~1,500/min (97% reduction)
  • Avg response: 80ms → 0.3ms (99.6% faster)
  • DB CPU: 95% → 12%
🎙️ Exact Script
  1. Define: "A cache is a fast temporary store — like Redis — that sits in front of slower data sources like databases."
  2. Pattern: "The most common pattern is cache-aside: check cache first, on a miss load from DB and populate the cache, with a TTL so data doesn't become permanently stale."
  3. Numbers: "A cache hit in Redis takes ~0.1–0.3ms. A DB query takes 10–100ms. Even a 90% hit rate reduces DB load by 10× at the same traffic level."
  4. Trade-offs: "The core trade-off is consistency vs speed. You must decide your TTL — too short and you lose the benefit, too long and users see stale data. Cache invalidation is notoriously hard: delete on write, or use event-driven invalidation."
  5. Problems: "The two failure modes I'd highlight: cache stampede — multiple simultaneous misses hammering the DB — solved with mutex locks or TTL jitter. And thundering herd on restart — solved with cache warming or gradual rollout."
  6. Close: "Caching is most powerful for read-heavy, rarely-changing data. I'd avoid caching highly personalized or rapidly changing data without very short TTLs."

How to Design for
High Availability

Redundancy, failover, health checks, SLAs, circuit breakers, and chaos engineering — building systems that stay up when things break.

Redundancy Failover Circuit Breaker SLA / SLO Chaos Engineering
✈️ The Airplane Analogy

Airplanes don't have one engine — they have two, three, or four. Not because one engine usually fails, but because if it does, you can't land and fix it mid-air. The cost of failure is catastrophic.

High availability systems are engineered the same way:

  • Redundancy — multiple copies of everything so one failure doesn't stop the whole system
  • Failover — when one thing breaks, another takes over automatically
  • Health checks — the plane constantly monitors each engine (not the pilot guessing)
  • Graceful degradation — fly with 3 engines, not crash because one is out
  • Chaos engineering — Netflix literally breaks their own systems on purpose to make sure the backup systems really work

High availability means: your system keeps working even when parts of it break.

High Availability (HA) is the property of a system that remains operational for a high percentage of time. It's measured as uptime percentage, often called "nines."

Key concepts:

  • SLA — Service Level Agreement: the uptime you promise customers (contractual)
  • SLO — Service Level Objective: the internal uptime target you engineer for (always higher than SLA)
  • SPOF — Single Point of Failure: any component whose failure brings down the whole system
  • MTTR — Mean Time to Recover: average time to fix an outage
  • MTBF — Mean Time Between Failures: average time between incidents
  • RTO — Recovery Time Objective: maximum acceptable downtime during a disaster
  • RPO — Recovery Point Objective: maximum acceptable data loss duration

  1. Frame with nines: "High availability is about eliminating single points of failure to hit a target uptime — typically 99.9% or 99.99% depending on business requirements."
  2. SPOF audit: "My first step is to map the architecture and identify every SPOF — any component whose failure takes down the system."
  3. Redundancy layers: "I'd add redundancy at every layer: multiple app server instances behind a load balancer, database primary with standby replica with automatic failover, and distribute across multiple availability zones."
  4. Failure handling: "Between services I'd use circuit breakers to stop cascading failures, retries with exponential backoff for transient errors, and timeouts to avoid hanging requests piling up."
  5. Numbers: "99.9% means 8.7 hours of downtime per year. 99.99% means 52 minutes. Each nine costs significantly more to achieve."
  6. Close: "True high availability isn't just architecture — it's tested. I'd use health checks, alerting, runbooks, and eventually chaos engineering to verify the system behaves correctly during failures, not just during normal operation."

How Load Balancing Works

Round-robin, least connections, consistent hashing, L4 vs L7, session affinity, and health checks — distributing traffic at scale.

Round-Robin Consistent Hashing L4 vs L7 Health Checks Session Affinity
🏦 The Bank Counter Analogy

Imagine a bank with 500 customers arriving at once, but only one teller. The queue is enormous and everyone waits an hour.

The bank opens 10 teller counters. But who decides which counter each customer goes to?

  • A greeter (the load balancer) stands at the entrance and directs each customer: "You go to counter 3, you go to counter 7."
  • The greeter makes sure no counter is overwhelmed while others sit idle
  • If a teller calls in sick (server crashes), the greeter stops sending customers there
  • Some greeters are smart — they send VIP customers (premium users) to the faster senior teller

A load balancer is exactly this greeter. It sits in front of your servers and distributes traffic so no single server gets crushed.

A load balancer (LB) is a network component that distributes incoming traffic across a pool of backend servers. It operates at different OSI layers:

L4 vs L7 Load Balancing

LayerSeesCan route byExample
L4 (Transport)IP + TCP/UDP packetsIP, port, protocolAWS NLB, HAProxy TCP mode
L7 (Application)Full HTTP requestURL path, headers, cookies, bodyAWS ALB, NGINX, Envoy

L7 is more powerful but adds latency (~1ms). L4 is faster but dumb — it can't route /api/* to one backend and /images/* to another.

Key Properties

  • Health checks — LB pings each server (e.g. HTTP GET /health every 5s) and removes failed ones from rotation
  • Session affinity (sticky sessions) — routes a user's requests to the same server, needed for stateful apps
  • SSL termination — LB decrypts HTTPS so backend servers handle plain HTTP

  • HAProxy — high-performance, L4/L7, battle-tested

  • Envoy — cloud-native proxy/LB, used as sidecar in service meshes

🎙️ Exact Script
  1. Define: "A load balancer distributes incoming traffic across multiple backend servers to prevent any single server from becoming a bottleneck or SPOF."
  2. L4 vs L7: "I'd choose based on needs. L4 load balancers route by IP and port — very fast, low overhead. L7 load balancers see the full HTTP request and can route by URL path, headers, or cookies — more powerful but add ~1ms."
  3. Algorithm: "The algorithm depends on the workload. Round-robin works for homogeneous stateless services. Least-connections is better for long-lived connections like websockets. Consistent hashing is essential when you're routing to stateful backends like distributed caches."
  4. Health checks: "Every LB should have health checks — polling a /health endpoint every 5–10 seconds and removing any server that fails N consecutive checks from the rotation."
  5. Sticky sessions: "For stateful apps I'd use session affinity — routing a user to the same server via cookie or IP hash. But I'd prefer to make the service stateless instead and store state in Redis."
  6. Close: "In production I'd also put the load balancer itself behind DNS-based failover or use two LBs in active-passive to avoid the LB becoming a SPOF."

How Microservices
Communicate

Synchronous REST/gRPC, async messaging, service discovery, API gateways, event-driven patterns, and the pitfalls of distributed systems.

REST / gRPC Message Queues Event-Driven API Gateway Service Mesh
🏢 The Office Building Analogy

Imagine a huge company that used to have one giant office with everyone crammed in together. Every decision required walking across the entire floor. It was slow, chaotic, and if one team was sick, everything stopped.

So the company split into departments — Sales, Engineering, Finance, HR — each in their own room. Now they're microservices. But they still need to talk to each other. How?

  • Phone calls (REST/gRPC) — "Hey Finance, what's Bob's salary?" Wait for reply. Fast and direct but the caller is blocked until Finance answers.
  • Email/Slack (message queues) — "Finance, please process this invoice." Drop it in their inbox and move on. No waiting. Finance processes it when ready.
  • Company-wide announcements (events) — "A new employee has joined." Anyone who cares (IT, HR, Finance) reacts. The announcer doesn't know who's listening.
  • Receptionist (API Gateway) — all outside visitors go through one front desk who routes them to the right department.

Microservices are independently deployable services that each own a specific business domain. They communicate over a network — unlike a monolith where functions call each other in memory.

Two Communication Modes

ModeDescriptionBest forExamples
SynchronousCaller waits for response; tight couplingReal-time queries, transactionsREST, gRPC, GraphQL
AsynchronousCaller doesn't wait; loose couplingBackground tasks, event notificationKafka, RabbitMQ, SQS, SNS

Key Distributed Systems Challenges

  • Network unreliability — calls can fail, timeout, or arrive out of order
  • Partial failures — a downstream service is slow; do you wait forever?
  • Data consistency — each service owns its DB; cross-service transactions require Sagas or 2-phase commit
  • Service discovery — how does Service A find the current IP of Service B? (Consul, Eureka, K8s DNS)
  • Observability — a request touches 10 services; where did it fail? (Distributed tracing: Jaeger, Zipkin)

import json

producer = KafkaProducer(bootstrap_servers='kafka:9092')

def place_order(user_id, items):
    # Sync: check stock + charge payment via gRPC
    inventory_client.check_and_reserve(items)    # gRPC ~5ms
    payment_client.charge(user_id, total)        # gRPC ~200ms

    # Async: fire event, don't wait
    event = {"user_id": user_id, "items": items, "total": total}
    producer.send('order.placed', json.dumps(event).encode())

    return {"status": "confirmed"}  # Returns in ~220ms
🎙️ Exact Script
  1. Two modes: "Microservices communicate in two modes: synchronous and asynchronous. The choice depends on whether the caller needs an immediate answer."
  2. Synchronous: "For real-time responses — like checking if a product is in stock before letting a user check out — I'd use REST for external APIs or gRPC for internal service calls. gRPC uses Protocol Buffers which are 3–10× smaller and faster than JSON."
  3. Asynchronous: "For background tasks — sending emails, updating analytics, triggering notifications — I'd publish events to Kafka or SQS. This decouples services so a slow email service doesn't block order placement."
  4. Infrastructure: "All external traffic routes through an API Gateway for auth, rate limiting, and routing. In large deployments I'd use a service mesh like Istio for automatic retries, mTLS, and distributed tracing between services."
  5. Hardest problems: "The hardest parts are distributed transactions — I'd use the Saga pattern instead of 2-phase commit — and debugging failures across services, which requires distributed tracing with a correlation ID."
  6. Close: "The guiding principle is: use synchronous calls when you need an answer now, use async messaging when you don't. Async makes systems more resilient — a consumer being down doesn't block producers."
