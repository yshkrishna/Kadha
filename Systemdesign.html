01 · How to Start the Interview L7 SIGNAL

Principal signal: You define the scope rather than accept whatever the interviewer implies. The candidate who skips this step designs the wrong system every single time.

📖 Story (Real-World Analogy)

Imagine you're a master architect hired to design a brand-new international airport. The city council says: "We need an airport." A junior architect immediately starts sketching terminal gates and runway layouts. A principal architect pauses and asks: "How many passengers per year? Domestic or international hub? Cargo or people? What's the budget ceiling? Are we on a swamp or solid rock?"

If you skip those questions, you might design a beautiful regional airport that collapses under the weight of 50 million international travelers—or a massive hub that bankrupts the city because it only services two flights a day. The core challenge in software is that an un-scoped design is a guaranteed failure, no matter how elegant the architecture.

💥 What Breaks Without It

Without the first 60 seconds of scoping, you design a system for the wrong scale. You propose a single Postgres instance with read replicas, but the interviewer secretly assumed 500M writes per day. Your design is instantly obsolete. You mention Kafka, but the interviewer only needs 100 requests/day. You've just over-engineered yourself out of a job.

Cascading failure of the interview itself: Wrong assumptions → wrong architecture → interviewer loses confidence → you start backtracking → time runs out while you defend an irrelevant design.

🧮 Back-of-Envelope Math

Scope negotiation math (before drawing anything):
• DAU estimate: 10M daily active users (reasonable FAANG assumption)
• Reads per user per day: ~50 → 500M reads/day
• Peak QPS: 500M / 86,400 × 3 (peak multiplier) ≈ 17,400 QPS
• Storage: 100M entities × 2KB = 200GB raw → ~$400/month on managed SSD
• Bandwidth: 17,400 × 1KB avg response ≈ 17 MB/s → ~140 Mbps peak
Conclusion: This forces a distributed cache layer and at least 3 app server instances.

❓ Clarifying Questions (The 5-Question Framework)

Q1: "Is read latency more critical than consistency, or would you rather guarantee no stale reads even at the cost of 50ms additional latency?"
WHY: Determines CP vs AP for data layer. ASSUMPTION: Read latency <20ms p99, eventual consistency acceptable.

Q2: "Are we optimizing for a global audience with multi-region writes, or single-region read-heavy?"
WHY: Multi-region writes add conflict resolution. ASSUMPTION: Single region, US-East.

Q3: "What is the expected write/read ratio? 1:100? 1:10?"
WHY: Drives caching strategy and DB sharding. ASSUMPTION: 1:50 read-heavy.

Q4: "Any hard compliance boundaries (GDPR, data sovereignty) that constrain data location?"
WHY: Blocks certain multi-region architectures. ASSUMPTION: No regulatory constraints.

Q5: "What is the one feature that, if it fails, causes the most business impact?"
WHY: Prioritizes reliability investment. ASSUMPTION: Core write path is critical.

⚖️ Trade-offs (Decision Framework)

02 · Back-of-Envelope Math L7 SIGNAL

Principal signal: You use math to ELIMINATE options, not just size components. "At this QPS, Option B costs 3× more than Option A for the same SLA — ruled out."

📖 Story (Real-World Analogy)

You're planning a massive wedding for 500 guests. A junior planner says: "Let's order cake!" A principal planner grabs a napkin and calculates: 500 guests × 1.5 slices per person = 750 slices. Each tier feeds 50 slices = 15 tiers minimum. The venue kitchen can only refrigerate 10 tiers. Without this math, you either run out of cake (angry guests) or order 30 tiers (bankrupt couple, wasted food).

The core challenge in software is that intuition about scale is almost always wrong — math is the only truth-teller.

💥 What Breaks Without It

Without envelope math, you design a system that looks beautiful on a whiteboard but melts at 1% of production traffic. You choose MongoDB because "it scales horizontally" — but your 50TB dataset doesn't fit in RAM, and without proper shard key math, one node melts while others idle.

Cascading failure: Wrong capacity estimate → insufficient instances → connection pool exhaustion → cascading timeouts → outage. Real example: the 2012 Obama campaign's AWS migration underestimated peak donation traffic by 7× — one Oprah tweet drove 50,000 concurrent donations that crushed their payment pipeline.

🧮 Back-of-Envelope Math (The Full Pipeline)

📐 Standard Estimation Pipeline:
Step 1 — DAU to QPS:
• 100M monthly active users → ~3.3M DAU (3% daily active rate)
• 3.3M users × 20 actions/day = 66M requests/day
• 66M / 86,400 seconds = 764 avg QPS
• × 3 peak multiplier = 2,292 peak QPS

Step 2 — Storage:
• 500M records × 2KB avg size = 1TB raw data
• × 3 (replication) = 3TB total
• × 1.5 (indexes, WAL) = 4.5TB provisioned
• ~$1,200/month managed Postgres SSD

Step 3 — Bandwidth:
• 2,292 peak QPS × 5KB avg response = 11.5 MB/s ≈ 92 Mbps
• ~$890/month data transfer costs

Step 4 — Server Count:
• 2,292 QPS ÷ 500 QPS per .NET 9 pod = 5 pods minimum
• + 2 for redundancy = 7 pods
• ~$403/month compute

💡 Surprising: Data transfer ($890) exceeds compute ($403). Total: ~$2,493/month.

❓ Clarifying Questions

Q1: "Is the 3× peak multiplier sufficient, or do we expect flash-crowd events (10× surge)?"
WHY: 10× surge requires auto-scaling buffer. ASSUMPTION: 3× daily peak.

Q2: "What's the read-to-write ratio? 100:1 means caching saves 99% of DB hits."
WHY: Determines Redis ROI. ASSUMPTION: 50:1 read-heavy.

Q3: "What is the acceptable data staleness window? 1 second? 5 minutes?"
WHY: Long TTLs reduce DB load. ASSUMPTION: 30-second staleness acceptable.

Q4: "Do we need full-text search?"
WHY: Full-text requires Elasticsearch, adding $500+/month. ASSUMPTION: Exact match only.

Q5: "What's the retention policy for logs?"
WHY: Observability storage often exceeds app storage. ASSUMPTION: 30-day retention, 50GB/day.

a) ❌ WRONG WAY

b) ✅ RIGHT WAY

/// <summary>Capacity plan derived from back-of-envelope math.</summary>
public sealed record CapacityPlan
{
    public int PeakQps { get; init; }
    public int DbMaxConnections { get; init; }
    public double RequiredCacheHitRatio { get; init; }
    public int PodCount { get; init; }

    public int ConnectionsPerPod => (int)(DbMaxConnections * 0.8 / PodCount);
    public bool IsDbSafe(double actualCacheHitRatio) =>
        PeakQps * (1 - actualCacheHitRatio) <= DbMaxConnections * 0.7;
}

public static class CapacityPlanner
{
    public static CapacityPlan FromDau(int dailyActiveUsers, int actionsPerUser)
    {
        int totalDailyRequests = dailyActiveUsers * actionsPerUser;
        int avgQps = totalDailyRequests / 86_400;
        int peakQps = avgQps * 3;
        int podCount = (int)Math.Ceiling(peakQps / 500.0) + 2;
        int dbMaxConnections = 500;
        return new CapacityPlan
        {
            PeakQps = peakQps,
            DbMaxConnections = dbMaxConnections,
            RequiredCacheHitRatio = 1.0 - (dbMaxConnections * 0.7 / peakQps),
            PodCount = podCount
        };
    }
}

c) Program.cs DI

builder.Services.AddSingleton(sp => {
    int dau = builder.Configuration.GetValue<int>("Capacity:DailyActiveUsers", 3_300_000);
    int actions = builder.Configuration.GetValue<int>("Capacity:ActionsPerUser", 20);
    var plan = CapacityPlanner.FromDau(dau, actions);
    var logger = sp.GetRequiredService<ILogger<CapacityPlan>>();
    logger.LogInformation("Capacity plan: PeakQps={PeakQps}, Pods={Pods}", plan.PeakQps, plan.PodCount);
    return plan;
});

d) Real Usage

[HttpGet]
public async Task<IActionResult> Search(string query)
{
    double currentHitRatio = await _metrics.GetCacheHitRatioAsync();
    if (!_capacity.IsDbSafe(currentHitRatio))
    {
        _logger.LogWarning("DB safety threshold breached. HR: {HR:P2}", currentHitRatio);
        return StatusCode(503, new { Message = "Service degraded — retry with backoff." });
    }
    return Ok(await ExecuteSearchAsync(query));
}

🎙️ Interview Script (Exact Words)

Opening: "Before I propose any architecture, I need to run the numbers. Can we agree on 10M DAU as a baseline? I'll use 3× peak multiplier unless you have a different spike pattern in mind."

While drawing: "I'm sizing the cache cluster based on the math: at 2,300 peak QPS and 500 DB connections, I need 85% cache hit ratio minimum."

🧠 Principal-level signal: "I always calculate the cost crossover point where managed services become cheaper than self-managed. At ~$2,500/month, managed Postgres is cheaper than the engineering hours to patch our own instance."

Closing: "To summarize: 2.3K peak QPS, 50:1 read ratio → 7 pods, Redis with 85%+ hit ratio, 3 DB nodes. Total ~$2,500/month. Biggest risk: cache stampede."

🔥 Failure Modes

1. Underestimated Peak: Marketing drives 7× traffic. Detection: QPS exceeds plan by 2× for 5min. Fix: Manual scale + queue.

2. Data Transfer Surprise: Cloud bill $12K instead of $2.5K. Fix: Enable compression, review CDN TTLs.

3. Cache Hit Ratio Cliff: TTL 5min but data changes every 2min. Fix: Reduce TTL, write-through caching.

4. Connection Pool Starvation: EF Core default MaxPoolSize not set. Fix: Explicit MaxPoolSize from CapacityPlan.

5. Forgot Observability Storage: 50GB/day logs = $800/month surprise. Fix: Sampling, 14-day retention.

💬 Follow-up Questions

Q: "Your math assumes uniform traffic. What if 90% of traffic hits 1% of endpoints?"
Principal: "Pareto distribution changes everything. I'd cache ~20 hot keys aggressively — 2MB of Redis. The cold tail still needs DB planning. This actually reduces Redis cost from $400 to $50/month."
