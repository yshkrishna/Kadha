01 · How to Start the Interview L7 SIGNAL

Principal signal: You define the scope rather than accept whatever the interviewer implies. The candidate who skips this step designs the wrong system every single time.

📖 Step 1 — Story (Real-World Analogy)

Imagine you’re a master architect hired to design a brand-new international airport. The city council says: “We need an airport.” A junior architect immediately starts sketching terminal gates and runway layouts. A principal architect pauses and asks: “How many passengers per year? Domestic or international hub? Cargo or people? What’s the budget ceiling? Are we on a swamp or solid rock?”

If you skip those questions, you might design a beautiful regional airport that collapses under the weight of 50 million international travelers—or a massive hub that bankrupts the city because it only services two flights a day. In software, the functional requirement (“design a URL shortener”) is the airport. The non-functional constraints (scale, latency, budget, consistency) are the soil, weather, and budget. The core challenge in software is that an un-scoped design is a guaranteed failure, no matter how elegant the architecture.

💥 Step 2 — What Breaks Without It

Without the first 60 seconds of scoping, you design a system for the wrong scale. You propose a single Postgres instance with read replicas, but the interviewer secretly assumed 500M writes per day. Your design is instantly obsolete. You mention Kafka, but the interviewer only needs 100 requests/day. You’ve just over-engineered yourself out of a job.

Cascading failure of the interview itself: Wrong assumptions → wrong architecture → interviewer loses confidence → you start backtracking → time runs out while you defend an irrelevant design. A real production parallel: Amazon’s 2021 US-EAST-1 outage happened partly because a scaling event in one subsystem wasn’t scoped against the blast radius of dependent systems. Scope mismatch kills systems.

🧮 Step 3 — Back-of-Envelope Math

⚡ Scope negotiation math (before drawing anything):
• DAU estimate: 10M daily active users (reasonable FAANG assumption)
• Reads per user per day: ~50 → 500M reads/day
• Peak QPS: 500M / 86,400 × 3 (peak multiplier) ≈ 17,400 QPS
• Storage: 100M entities × 2KB = 200GB raw → ~$400/month on managed SSD
• Bandwidth: 17,400 × 1KB avg response ≈ 17 MB/s → ~140 Mbps peak
Conclusion: This forces a distributed cache layer and at least 3 app server instances. A single DB node cannot handle 17K QPS.

❓ Step 4 — Clarifying Questions (The 5-Question Framework)

Q1: "Is read latency more critical than consistency, or would you rather guarantee no stale reads even at the cost of 50ms additional latency?"
WHY: Determines CP vs AP for the data layer. ASSUMPTION: Read latency < 20ms p99, eventual consistency acceptable.

Q2: "Are we optimizing for a global audience with multi-region writes, or is this a single-region system with a read-heavy pattern?"
WHY: Multi-region writes add conflict resolution complexity. ASSUMPTION: Single region, US-East.

Q3: "What is the expected write/read ratio? 1:100? 1:10?"
WHY: Drives caching strategy and DB sharding. ASSUMPTION: 1:50 read-heavy.

Q4: "Are there any hard compliance boundaries (GDPR, data sovereignty) that constrain where data can reside?"
WHY: Blocks certain multi-region architectures. ASSUMPTION: No regulatory constraints initially.

Q5: "What is the one feature that, if it fails, causes the most business impact? We'll design the reliability budget around that."
WHY: Prioritizes resilience investment. ASSUMPTION: Core write path is the critical function.

⚖️ Step 6 — Trade-offs (Decision Framework)

Option A: Full microservices from day one. Pros: team autonomy, independent scaling. Cons: 10× operational complexity, high latency tax. Cost: $12K/month. ❌

Option B: Modular monolith with clear boundaries. Pros: simple deploy, low latency. Cons: limited scaling granularity. Cost: $3K/month. ✅

Option C: Serverless functions. Pros: zero ops. Cons: cold starts, vendor lock-in. Cost: variable.

🏆 Recommendation: Option B for now. Extract services only when two of three criteria are met: independent scaling, team boundary, or technology divergence.

💻 Step 7 — .NET 9 Code

a) ❌ WRONG WAY

// ❌ No scope validation, assumes happy path
app.MapGet("/design", () => "Here's my perfect design!");

b) ✅ RIGHT WAY

/// <summary>Principal-level scope negotiation filter.</summary>
public record Scope Boundary(int MaxQps, string ConsistencyModel);
public static class InterviewStartup {
    public static ScopeBoundary DefineScope(int dau, int readsPerUser) {
        int peakQps = (dau * readsPerUser) / 86400 * 3;
        return new ScopeBoundary(peakQps, "eventual");
    }
}

c) Program.cs DI

// NuGet: MediatR, OpenTelemetry.Extensions.Hosting
builder.Services.AddSingleton<ScopeBoundary>(sp => 
    InterviewStartup.DefineScope(10_000_000, 50));

d) Real Usage

app.MapGet("/scope", (ScopeBoundary scope) => 
    Results.Ok($"System designed for {scope.MaxQps} QPS"));

e) Unit Test

[Fact] public void DefineScope_ValidInput_ReturnsCorrectPeak() {
    var scope = InterviewStartup.DefineScope(10000000, 50);
    Assert.True(scope.MaxQps > 15000);
}

📈 Step 8 — Scaling Stages

Stage 1 (0→1K): Single pod, SQLite. Don't need Redis. Cost: $50/month.

Stage 2 (1K→100K): Postgres, basic caching. Trigger: CPU > 60%. Cost: $400/month.

Stage 3 (100K→10M): K8s cluster, Redis, CDN. Cost: $3,200/month.

Stage 4 (10M+): Multi-region active-active. Cost: $22,000/month.

🎙️ Step 9 — Interview Script (Exact Words)

Opening: "Before I draw anything, I'm going to define the non-functional requirements that will drive every architectural decision. I'll state my assumptions explicitly—please stop me if any are wrong."

While drawing: "I'm adding a cache here because at ~17K QPS the DB would need 4 read replicas without it, costing $2,400/month more than a Redis cluster."

When stuck: "I haven't encountered this exact constraint in production, but based on the latency budget, I'd reason about it like this..."

🧠 Principal-level signal: "I always validate the SLO budget before picking a database. If we need 99.99% uptime, that's 52 minutes of downtime per year—Postgres with async replication can hit that without the complexity of multi-primary."

🔥 Step 10 — Failure Modes

1. Scope Creep Death: Interviewer adds requirements silently. Detection: You notice contradictions. Fix: "Let me update my assumptions."

2. Missing SLA anchor: You design without latency target. Fix: State p99 < 100ms.

💬 Step 11 — Follow-up Questions

Q: "Why didn't you ask about the tech stack?"
Principal answer: "The stack is an implementation detail. I care about scale, consistency, and cost first—any modern stack can implement the architecture."

⚓ Step 12 — Memory Anchor

Analogy: The airport architect who asks about soil before designing runways.

Numbers: 17K QPS = peak for 10M DAU. 52 min/year = 99.99% uptime budget. 3× peak multiplier.

Principal signal phrase: "I define scope by SLO budget, not by whatever the interviewer implies."

🕒 Step 13 — Production Reality Check

3AM Scenario: PagerDuty fires: "p99 latency > 2s for /api/scope". Redis eviction rate spiked because a bad deploy doubled cache key size. Memory hit 98%.

First 10 minutes: Check Redis memory graph → roll back deploy → flush large keys.

Leadership call: "A configuration change caused memory pressure in our caching layer, slowing down the core API. We've rolled back and are restoring performance. No data loss, full recovery in 5 minutes."

Postmortem: Root cause: missing memory limit guardrail in CI/CD. Action: add automated capacity test for cache memory footprint.

Permanent fix: Implement cache key size governance and automated rollback on memory threshold breach.
